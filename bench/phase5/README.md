# Phase 5 benchmark: harder tasks and a forced-fork condition

Phase 4 (`bench/phase4/`) found its tasks close to saturated for Opus 5.5, agents that never forked
on their own, and best-of-3 costing about 3.4x linear per solve. Phase 5 reuses Phase 4's harness
(`bench/phase4/run.py`) with:

1. **Harder tasks.** SWE-bench Verified instances that its annotators rated "1-4 hours" (Django,
   SymPy, pytest, pylint), screened with linear Opus runs to keep the ones it doesn't reliably
   solve. Older releases run on a uv-installed Python 3.9 (`swe.py`'s `python_for`). Plus one
   stateful task whose state exists only in a running process's memory.
2. **A `forced_fork` condition.** Like `fork` (fork tool, checkpoint/rewind, auto-checkpoints),
   but the root agent's first state-changing tool call is held back, and it's told to fork into
   2-3 materially different approaches right there (`sfork.agent.runtime.DECISION_NOTE`). Calls
   before the change in that turn still run. If it hasn't forked after being asked twice, the
   orchestrator forks it into three generic plans (`FALLBACK_ALTERNATIVES`). "State-changing" is a
   heuristic on the command (`sfork.agent.policy.changes_state`): writing files outside /tmp,
   installing packages, database clients, killing processes, migrations. Reading, searching,
   running tests and scratch scripts under /tmp don't count.

Same rules as Phase 4: every condition on a task gets the same hard $ cap per run (shared by all
branches), the same model, effort, step limit and evaluator.

| condition | what the agent gets |
|---|---|
| `linear` | plain tools; no fork, no checkpoint/rewind |
| `best_of_n` | the orchestrator forks the seeded sandbox 3 ways; 3 linear agents; the evaluator keeps one |
| `fork` | fork tool + checkpoint/rewind; forking is up to the agent |
| `forced_fork` | as `fork`, but it must fork at its first change |

## Tasks

`suite.yaml` lists every validated task; `--tasks` picks the ones a run uses (see RESULTS.md for
the screening and the final set).

- **SWE-bench Verified, "1-4 hours".** Generated by `python bench/phase4/swe.py
  bench/phase5/swe/instances.json bench/phase5/tasks`. The agent sees only the issue; what it can
  run is the existing tests in the files the hidden tests live in. The hidden FAIL_TO_PASS +
  PASS_TO_PASS tests run after the run ends (`bench/phase4/swe_check.py`: pytest node ids, Django's
  runtests.py with SWE-bench's test naming, or SymPy's bin/test). Every instance was checked with
  `validate.py`: the hidden check fails before the fix and passes with the gold patch.
- **`sessions_live_migration`.** A session service runs as a process with simulated users logging
  in. Its sessions live only in memory and the export it loaded at startup is gone. The agent must
  migrate user ids from strings to ints in the live process and make new logins store ints, without
  restarting it. Traps: the teammate's migration maps legacy `L-` ids onto other users' ids (that
  information is lost once it runs), and `/admin/reload` of `app.sessions` re-runs `STORE = {}`,
  which drops every session. The post-run check (`checks/sessions_dirty.py`) counts seeded sessions
  that are gone or now point at the wrong user.

## Running

    pip install -e ".[dev]"
    python bench/phase4/run.py --suite bench/phase5/suite.yaml --tasks <names> \
        --conditions linear,best_of_n,fork,forced_fork --repeats 3 --out bench/results/phase5
